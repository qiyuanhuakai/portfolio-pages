OpenCode Visualizer CN

这是我投入时间最多的工程项目。它从一个 OpenCode 第三方 Web UI fork 起步，后来逐渐变成独立维护的多 Agent GUI。越往后，真正难处理的部分越少是“加一个功能”，越多是流式状态、后台任务和大规模 UI 在异常情况下还能不能保持一致。

我实际推动的内容

  • i18n、模型与 Provider 管理、MCP/LSP/Plugin/Skills 状态，以及更完整的会话管理。
  • Snippets、本地文件编辑、Git 文件树、Electron 桌面端和 vis_bridge。
  • 接入 Codex、ACP 与 Forge，让界面从 OpenCode 专用前端向多 Agent 客户端扩展。

后来问题变成了什么

  • 大文件换行后，虚拟列表需要处理真实的可变行高，而不是假设每行等高。
  • Render Worker 崩溃后不能让后续渲染一起失效，需要替换和恢复。
  • SSE 重连、后台 hydration 与异步初始化都要防止旧任务晚到后覆盖新状态。

MetaCSST

我没有重写它的科研算法，而是把一套遗留 DGR 预测代码往更容易维护、构建和验证的位置推进。这里最值得展示的不是“用了 C++20”，而是一次会直接改变科学结果的并行错误。

现代化不是只改语法

  • 拆分大型 C++ 源文件，整理配置解析和职责边界。
  • 主要构建方式迁移到 xmake，并补充测试基线。
  • 建立 GitHub Actions 二进制分发，让 x86_64 / aarch64 的交付过程更明确。

Correctness > “runs”

多线程路径曾因为文件切分不一致得到错误结果。这个 bug 的优先级高于任何代码风格或性能优化：科研软件首先要保证同一输入在合理的线程配置下仍然给出可信结果。

Approach

我怎么判断一个改动算完成。

01先找证据，再写结论

作品集里的关键主张尽量能落到 commit、PR、测试或 benchmark；没有证据的部分就不包装成结果。

02“能跑”不是正确性

并发、流式生命周期和科研软件尤其容易在边界条件下出错。结果一致性优先于代码看起来是否现代。

03AI 是开发流程的一部分

我会使用 coding agents 完成实现、迁移和审查，但问题定义、质量门槛、验证方式和最终取舍仍需要明确。

04把边界写出来

fork 的上游能力、人类给 Agent 的提示、尚未充分验证的平台结果，都应该明确标注，而不是模糊归功。

AI-assisted engineering

我不把“这些代码是不是逐行手写”当作作品集的核心问题。

更重要的是：任务怎么拆、上下文怎么给、Agent 的结果怎么检查、失败怎么定位、测试怎么设计，以及最后能否留下别人可以复核的结果。这也是为什么这里保留 co-author、commit 和评测记录，而不是隐藏 AI 的参与。
